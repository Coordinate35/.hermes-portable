# 路线耗时估算（步行／骑行／驾车／公共交通）

用户常问「从 A 到 B 走路/骑车多久」「这地方离公司多远」「坐地铁公交怎么走」。OSM 免 key、可复核，先出底数；要国内口径（公交/地铁班次、步行天桥、主辅路）走百度网页版自动化。默认两家并列并标清数字属于哪家口径。

## 口径由用户定
- 用户没指定：OSM 出底数 + 百度校口径，两家并列，标明来源。
- **用户点名一家（「不要用 OSM，就用百度」）→ 只报该家**，不得再混另一家的数字；若之前混过，明说「按百度口径是 X，之前的 Y 作废」，不要两个数并排糊过去。
- 被追问时先分清是在改**口径**（哪家数据）还是改**假设**（哪个门、出发时间、交通方式），再重算。

## When to Use
- 「从 X 到 Y 走路/骑车多久」「这地方离公司多远」「通勤要多久」
- 用户要求「用最近的门/最近的入口」算，而不是到地块中心
- 需要可复核的距离—时间数字，而不是口头估个大概

## 流程

### 1. 地名先落坐标，不要凭印象
```
https://photon.komoot.io/api/?q=<urlencode>&limit=5
```
返回 `properties.name/osm_value/district` + `geometry.coordinates`（`[lon, lat]`，注意顺序）。

- 同名多地用 `district`/`city` 区分。
- 公司名+楼号常直接命中 POI（「大钟寺2号楼」→「抖音 大钟寺广场2号楼」）。**命中后把 POI 全名回报给用户确认**，别默默当起点——「2号楼」这类简称可能指办公楼也可能指住宅楼。

### 2. 算路线（三套 profile 分开请求）
```
https://routing.openstreetmap.de/routed-foot/route/v1/foot/<lon>,<lat>;<lon>,<lat>?overview=false
https://routing.openstreetmap.de/routed-bike/route/v1/bike/<lon>,<lat>;<lon>,<lat>?overview=false
https://routing.openstreetmap.de/routed-car/route/v1/driving/<lon>,<lat>;<lon>,<lat>?overview=false
```
读 `routes[0].distance`（米）与 `routes[0].duration`（秒）。

⚠️ `router.project-osrm.org` 的 demo 只有驾车 profile：传 `foot`/`bike` 也返回同一套驾车数字，**不能用来算步行骑行**。

### 2b. 公共交通（公交/地铁）
百度网页版切到「公交」后一次给出多条方案，每条带 `票价 / 耗时 / 距离 / 步行米数`；点某一行（`.route-head`）展开站点级明细：哪站上车、方向、几站、哪个出口、分段步行。面板顶部还有「最快 / 少换乘 / 少步行」三个排序 tab。

判读：**把步行米数当第一指标**。耗时最短的方案常要走 800 m 以上，骑车的门到门时间反而更优——两个数并排给用户，别只报第一名。

### 3. 目标是小区/园区（一个面）时：门跟着交通方式走
「最近的门」不是唯一答案，取决于**从哪一侧过来**：
- 步行/骑行/驾车（起点直达）→ 取离**起点**最近的边界；
- 公交/地铁 → 取离**下车站**最近的出入口，而不是离起点最近的。锁错门会多走几百米、总时间多算 5 分钟以上。

实操：**终点不要带「-南门」这类后缀**，直接 route 到小区/园区整体 POI，让引擎自己挑入口；要核对时把北/南/东/西四条边界各取一个点分别算，横向比。

OSM 多数小区没画门，所以仍要说清「按 X 侧边界算，进小区还要再走 x 分钟」，并把门名问一句锁定，下次不必重猜。

### 3b. 分段叠加（接驳 + 干线 + 接驳）
用户可能要求「按分段算：门→地铁站骑车、地铁、站→目的地骑车，再加起来」。做法是每段单独 route、**同一口径**，再补固定成本：

| 段（实测，百度口径） | 步行 | 骑行 |
|---|---|---|
| 小区西门 ↔ 地铁站 | 8 min / 480 m | 7 min / 1.1 km |
| 地铁站 ↔ 办公楼 | 2 min / 120 m | 4 min / 580 m |

- 固定成本别漏：进出站+安检+等车 ≈ 4 min（短程 2 站），找车/还车 ≈ 2–3 min **每端**。
- **600 m 以内的接驳段，步行通常不慢于骑行**：百度会给 120 m 的直线段规划出 580 m 的骑行路（绕单行/主路），骑反而慢 2 min。所以「骑行接驳」不是默认更快，逐段比过再下结论。
- 分段之和要与端到端结果对齐（实测 21 min vs 21 min）；差 >2 min 必须说明差在哪（等车、找车、绕行），不能两个口径混着报。

### 4. 回报格式
距离 + 时间 + **直线距离** + 一句绕行原因（铁路、快速路立交、单行）。给区间不给单点：快走/慢走、含等灯各一个数。默认不拉逐步转向，用户要再给。

## 口径与局限（必须讲，别把估算说成保证）
- OSM 无实时路况、无红绿灯计时；北京的小路口、天桥、桥洞覆盖不如高德细，实际常差 5–10 分钟。
- 距离是路网距离：直线 2.4 km 走成 3.3 km，中间多半隔着铁路或立交，这个差要主动解释，否则数字看着像错的。
- 国内口径要真实数就走百度网页版，可用 browser_exec 自动化（配方见 `references/baidu-map-web-ui.md`）。高德 `ditu.amap.com` 点「走路去」弹扫码登录，无账号到不了结果页，别在上面耗时间；`m.map.baidu.com` 解析不到，也别试移动版。
- 两家差异是真实的，不是误差：同一段路骑行百度 4.8 km / 28 min、OSM 3.8 km / 20 min（百度只走主干道辅路）。报数时把两家口径并列、说明差异来源，别只给一家还装作精确。
- 报数字时带上计算时间点（如「2026-11-11 19:35 算的」），路况与门禁会变。

## 脚本
`scripts/route.py` 一次算三种方式，输出距离/耗时/直线距离：
```bash
PYTHONPATH= /usr/bin/python3 scripts/route.py "抖音大钟寺广场2号楼" "展春园小区"
PYTHONPATH= /usr/bin/python3 scripts/route.py "116.33706,39.96450" "116.33681,39.98558"
```
坐标参数按 `lon,lat` 顺序。

`scripts/wgs2bd.py`：WGS84 → GCJ02 → BD09 转换。只有要按经纬度直接调百度时才用（百度是 BD-09，直接喂 OSM 坐标会偏 500 m 左右）；用地名+联想项调路线则不需要。

`scripts/bd_poi_enum.py "小区名"`：走百度 su 接口枚举该地名下所有 POI（含北/南/东/西门），回答「这小区有哪些门」时先跑它，别凭方位猜。
